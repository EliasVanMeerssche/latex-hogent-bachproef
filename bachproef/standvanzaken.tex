\subsection{Introductie en Basisconcepten}
Om te begrijpen welke functies in de kernel gebruikt worden om rootkits in te laden moet er gekeken worden naar verschillende mogelijke aanvalsmethodes. Volgens \textcite{nagy2025detecting} zijn er drie manieren om een rootkit in te laden en twee manieren om de kernel module te verstoppen. Deze worden hieronder beschreven. De eerste methode wordt \emph{Loadable kernel module (LKM)} genoemd, deze wordt normaal gebruikt voor het inladen van drivers. Drivers kunnen op deze manier eenvoudig toegevoegd worden, zonder het systeem te herstarten. Dit zorgt er ook voor dat de kernel niet helemaal opnieuw moet gecompileerd worden om nieuwe modules in te laden. Deze methode kan ook worden gebruikt voor het inladen van rootkits. Na het inladen probeert de module zichzelf te verstoppen om detectie te voorkomen.
De tweede methode is \emph{Return-oriented programming (ROP)}, dit kan gebeuren wanneer de aanvaller een  memory corruption vulnerability vindt.
De derde methode is \emph{Extended Berkeley Packet Filter (eBPF)}. Dit is een eenvoudig alternatief voor LKM-rootkits omdat het in een sandbox omgeving runt waardoor het geen systeemcrash kan veroorzaken, in tegenstelling tot LKM-rootkits. Omdat een LKM direct in de kernel draait, kan een simpele programmeerfout het geheugen van de kernel of de gebruiker corrumperen. Dit resulteert in een fatale fout die een kernel panic wordt genoemd, wat het hele besturingssysteem laat vastlopen en een herstart vereist. Ze maken beide gebruik van \emph{Function hooking}.
Volgens \textcite{zacharia-mansouri-2026-NReUKT} is een LKM sterk afhankelijk van specifieke kernel versies en moet vaak opnieuw worden gecompileerd voor kleine kernel-updates, omdat interne kernel structuren per versie verschillen. eBPF is eenvoudiger om mee te werken want het maakt gebruik van \emph{CO-RE (Compile Once, Run Everywhere)}. Hierdoor kan eBPF-code één keer worden gecompileerd en dynamisch op verschillende kernel versies draaien zonder hercompilatie. 

Nog een groot verschil tussen LKM-rootkits en eBPF is hoe ze  worden ingeladen. Een LKM wordt ingeladen als een traditionele module (vaak een fysiek bestand) in het besturingssysteem \autocite{Windshock2025}. In tegenstelling tot eBPF-programma's, die via de bpf() systeemaanroep direct ingeladen worden in de eBPF virtuele machine van de kernel. Hierdoor bestaat er niet direct een module-bestand op het bestandssysteem \textcite{Zaidenberg2024}. Dit maakt eBPF inherent heimelijker (stealthier) dan een LKM.

Een LKM heeft onbeperkte toegang en kan direct willekeurige kernelgeheugenlocaties of kernel-datastructuren (zoals de syscall table of gebruikersrechten) fysiek overschrijven. eBPF is sterk beperkt: het kan niet zomaar willekeurige functies aanroepen of kernelgeheugen fysiek overschrijven \autocite{zacharia-mansouri-2026-NReUKT}. eBPF moet altijd gebruikmaken van toegestane helper-functies (zoals bpf\_probe\_write\_ user) om indirect data of retourwaarden te manipuleren \textcite{Zaidenberg2024}.

Tenslotte is \emph{Function hooking} een methode om functies te overschrijven. Als de rootkit ingeladen is, heeft het macht over de originele functies van de kernel. Dit zorgt ervoor dat het deze originele functies kan overschrijven. Het kan de locatie van specifieke bestanden obfusceren waardoor het detectie kan omzeilen. Er is een verschil tussen eBPF-rootkits en LKM-rootkits bij function hooking. \emph{Direct Kernel Object Manipulation} is een andere techniek om te verbergen dat een kwaadaardige module is ingeladen. Deze methode past het kernelgeheugen aan waardoor het de locatie van bestanden zoals de kernel module kan verwijderen \autocite{nagy2025detecting}.

\subsection{Tracingtechnologieën in Linux}
Volgens \textcite{zacharia-mansouri-2026-NReUKT} heeft LKM veel meer vrijheid met onbeperkte rechten over het systeem. De code in de hook kan willekeurige functies aanroepen en elk deel van het kernel- en gebruikersgeheugen direct lezen of schrijven. Dit is niet zo bij een eBPF. Hierbij is het extreem gelimiteerd wat de code mag doen binnen de hook. In plaats daarvan zijn ze strikt afhankelijk van een specifieke lijst met goedgekeurde eBPF helper-functies om acties en manipulaties uit te voeren. Omdat LKM-rootkits directe geheugentoegang hebben, haken ze functies vaak vast op agressievere manieren. Een klassieke LKM-methode is bijvoorbeeld het fysiek en direct overschrijven van pointers in de \emph{syscall} table (de systeemaanroeptabel) van de kernel. In tegenstelling kan eBPF interne kernel structuren zoals de \emph{syscall} table niet rechtstreeks aanpassen. Om functies te hooken, maakt het uitsluitend gebruik van specifieke, veilig ingebouwde inhaakpunten in de kernel, zoals \emph{Kprobes}, \emph{Uprobes}, en \emph{Tracepoints}. Ook al kan een LKM ook gebruik maken van deze hooks is dit minder nuttig aangezien het krachtigere tools kan gebruiken.

Er zijn verschillende soorten hooks, die hierna worden besproken. \emph{Uprobes} zijn hooks op functies in de \emph{userland}. Dit zou gebruikt kunnen worden om bepaalde gebruiker programma's functies aan te roepen en aan te passen. Een tweede soort hook is \emph{Kprobes}. Deze hook verschilt van Uprobes omdat het functies aanroept binnen de kernel space. De lijst van functies die aangeroepen kan worden staat in /proc/kallsyms \textcite{Heredia2021}. Er is wel een lijst van functies die hiervoor niet gebruikt mogen worden. Het nut van Kprobes is om mee te kijken naar wat het systeem aan het doen is. Dit is bedoeld als een debugging tool. 
Er bestaan ook nog \emph{Tracepoints} maar deze zijn statisch op voorhand in de kernel verankerd door de makers.
Volgens \autocite{zacharia-mansouri-2026-NReUKT} is er een netwerk hook genaamd \emph{Express Data Path (XDP)}. Dit biedt de mogelijkheid om eBPF-programma's uit te voeren op het laagst mogelijke punt van de netwerkstack: direct op de netwerkkaart (NIC), nog voordat de pakketten door de kernel of de firewall worden verwerkt.  
\emp{Function Tracer (ftrace)} is een veel gebruikte kerneltool om te debuggen en analyse te doen over systeemprestaties. Het maakt gebruik van een universele methode om willekeurige kernelfuncties te hooken \textcite{NAGY2025301928}. Ftrace voegt namelijk aan het begin van elke kernelfunctie standaard een \_\_fentry\_\_() functieaanroep toe. Een LKM kan hierop inhaken en direct de status van de processorregisters aanpassen. Dit zorgt ervoor dat de aanvaller de functie kan omleiden naar zijn eigen kwaadaardige functie in plaats van zijn eigen functie uit te voeren \textcite{Apriorit2022}. Om dit mogelijk te maken, wordt de kernel gecompileerd met speciale compiler-opties (-pg en -mfentry) die ervoor zorgen dat er aan het prille begin van vrijwel elke kernelfunctie een aanroep naar de traceerfunctie \_\_fentry\_\_() wordt ingevoegd. Om het systeem niet onnodig te vertragen, vervangt de kernel deze aanroepen standaard door nutteloze nop (no-operation) instructies \textcite{Apriorit2022}.

\subsection{Offensieve Mogelijkheden: eBPF en LKM Rootkits}
Hoewel hooks zoals Kprobes, Uprobes en Tracepoints oorspronkelijk zijn ontworpen voor debugging en monitoring en in de basis alleen read-only toegang geven tot de parameters van de gehookte functie, kunnen ze toch worden misbruikt om data aan te passen. Als een eBPF-programma hookt op een functie krijgt het het argument waarmee die originele functie is aangeroepen. Dit zijn vaak pointers naar geheugenlocaties in userland. Met dit proces krijgt de aanvaller de locatie waar de data zich precies fysiek bevindt. De functie bpf\_probe\_write\_user() wordt dan gebruikt door een bevoorrecht eBPF-programma om direct data in de virtuele geheugenruimte van de gebruiker te overschrijven \textcite{Heredia2021}. De rootkit leest de geheugenbuffer via de hook uit en gebruikt deze helper-functie vervolgens om de data op dat adres stilletjes aan te passen, zoals het manipuleren van het bestand /etc/sudoers wanneer dit in het geheugen wordt ingelezen \autocite{zacharia-mansouri-2026-NReUKT}. 

De rootkit plaatst een hook op het exit-\emph{tracepoint} van de systeemaanroep (sys\_exit\_getdents64). Het moet namelijk wachten tot de kernel daadwerkelijk klaar is met het vullen van de buffer met de bestandsinformatie.
Zodra de buffer is gevuld, gebruikt de rootkit zijn "schrijfrechten" in de user buffer via de functie bpf\_probe\_write\_user() om in de linux\_dirent64-structuur de d\_reclen-waarde (het lengte-attribuut) van het bestand dat net voor het te verbergen bestand staat, te overschrijven en te vergroten \textcite{Heredia2021}.

\emph{XDP} kan een \emph{eBPF} programma de mogelijkheid om een \emph{Command & Control} op te zetten. Aanvallers gebruiken dit om te luisteren naar "magic packets". Zodra een XDP-programma zo'n commando herkent, voert het de taak uit en overschrijft het pakket direct met onschuldige data (zoals een HTTP health check). Hierdoor merken het besturingssysteem en de netwerkmonitoringstools helemaal niets van de kwaadaardige communicatie \textcite{zacharia-mansouri-2026-NReUKT}. 

\subsection{Beveiliging en Beperkingen vanuit het Besturingssysteem}
Er bestaan verschillende beveiligingsmechanismen in de Linux-kernel om kernel exploits tegen te gaan. Dit wordt beschreven in \textcite{takaronis2024linux} en \textcite{LKMPwnPart1}. Het eerste is \emph{SMEP (Supervisor Mode Execution Prevention)}. Dit voorkomt dat een aanvaller die een kernel exploit heeft uitgevoerd en macht heeft gekregen over de RIP (Register Instruction Pointer) dit kan gebruiken om de pointer te verwijzen naar een eigen stuk code. \emph{SMEP} zorgt ervoor dat alles in de userland niet uitgevoerd mag worden. De RIP is een CPU-register met het geheugenadres van de volgende instructie. Als iemand dit overneemt kan men de instructie geven om zijn eigen script uit te voeren.
Het tweede beveiligingsmechanisme is \emph{SMAP (Supervisor Mode Access Prevention)}. Dit zorgt ervoor dat geheugen van \emph{userland} niet mag beschreven of gelezen mag worden. Deze beveiliging bestaat omdat aanvallers gebruik maken van  ROP-gadgets. Deze bevatten stack-pointers die verwezen kunnen worden naar wat de aanvaller beheerst. De aanvaller plaatst dit dan in de \emph{userland}, \emph{SMAP} voorkomt dan dat de kernel kan lezen of uitvoeren. 
\emph{KASLR (Kernel address space layout randomization)} is een derde beveiligingsmechanisme dat ervoor zorgt dat de geheugenlocaties van de kernel random bepaald worden bij het booten van het systeem. 
Tenslotte zorgt \emph{KPTI (Kernel Page-Table Isolation)} ervoor dat de page tables verdeeld zijn over user page tables en kernel page tables. De verschillende beveiligingsmechanismen zullen omzeild moeten worden door de exploits.  

Ftrace is hier uniek in dat het mogelijk is om functionaliteit van een hook uit te zetten voor de veiligheid. De rest van de besproken methodes kunnen dat niet zomaar. Voor het limiteren van hoeveel een eBPF rootkit kan doen zijn er verschillende opties. Volgens \autocite{Instatunnel2023} kun je instellen dat alleen gebruikers met privileged access eBPF kunnen inladen. Dit gebeurt met kernel.unprivileged\_bpf\_disabled = 1. Het is ook mogelijk om eBPF volledig uit de kernel te halen, dit is een optie die meegegeven moet worden tijdens het compileren van de kernel \textcite{Windshock2025}.

Legitieme kernelmodules kunnen zichzelf beschermen tegen ongewenste ftrace-hooks door de interne datastructuren van ftrace te manipuleren. Ftrace bewaart data over hooks in zogeheten ftrace-pagina's met dyn\_ftrace structuren. Door de dyn\_ftrace records van specifieke functies te verwijderen en deze te overschrijven met nutteloze nop (no-operation) instructies, wordt het voor een rootkit onmogelijk gemaakt om via ftrace een hook op die specifieke functie te plaatsen \textcite{Apriorit2022}.

Volgens \autocite{Zaidenberg2024} bestaan er tools zoals Tracee en Falco die waarschuwen voor ongeautoriseerd gebruik van eBPF. Falco is een open-source \emph{Host Intrusion Detection System (HIDS)}, het maakt zelf gebruik van eBPF. Het kijkt naar specifiek  bpf() en perf\_event\_open systeemaanroepen. Omdat malware deze aanroepen moet gebruiken om eBPF-code in de kernel te laden, genereert Falco direct op regels gebaseerde waarschuwingen. Tracee is een runtime security en forensics tool die ook eBPF gebruikt om het systeem te beveiligen. Een functie waar het zich op richt is het bpf\_attach event. Dit event wordt door de kernel aangemaakt op het exacte moment dat een eBPF-programma zich probeert vast te haken aan een tracepoint, kprobe of uprobe. Zodra Tracee dit ontvangt krijgt het belangrijke informatie van het eBPF-programma zoals het ID, de naam en het type van programma, ook krijgt het de specifieke eBPF helper-functies die gebruikt zijn. 

\subsection {Detectiemethoden}
Elk rootkit zorgt ervoor dat het zo moeilijk mogelijk te detecteren is. Hierdoor zijn de standaard commando's om actieve eBPF-programma's weer te geven van weinig nut. Er zijn andere manieren om toch rootkits te detecteren ook al is het systeem zelf onvertrouwbaar. Door een betrouwbare momentopname (snapshot) van het RAM-geheugen te maken via een hypervisor wordt het probleem omzeild. Tools zoals Volatility framework kunnen offline analyses maken van het RAM-geheugen \textcite{Zaidenberg2024}. Tools die ook besproken zijn in het onderdeel van preventie zoals Falco kunnen ook gebruikt worden om rootkits op te sporen als het systeem al besmet is \textcite {Windshock2025}.  

\subsection {De Evolutie van Rootkit-technieken}
Volgens \autocite{Heredia2021} verandert de wereld van rootkits voortdurend. Nieuwe ontwikkelingen van zowel Red Hats als Blue Hats zorgen ervoor dat de ontwikkeling van rootkits nooit stilstaan. Een eenvoudig voorbeeld hiervan zijn eBPF-rootkits. het is een vrij recente ontwikkeling, waar kernel-rootkits voorheen vrijwel uitsluitend als Loadable Kernel Modules (LKM) werden ontwikkeld. eBPF staat momenteel centraal als het over rootkit-ontwikkeling gaat. Aanvallers verleggen hun focus naar eBPF omdat het, in tegenstelling tot LKM-rootkits, op veel moderne systemen standaard is ingeschakeld en het toelaat om onzichtbaar code in de kernel te draaien zonder nieuwe kernelmodules te hoeven laden \textcite{Heredia2021}
